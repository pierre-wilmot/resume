A real example

Two hours to five minutes.

At a major European financial exchange, the only way to test backend business logic was to boot the entire system.

— Before
Boot full backend stack
Boot client application
Craft a network request
Send through networking layer
Wait for full processing cycle
Observe result

~2 hrs per iteration
+ After
Compile business logic module only
Run unit tests directly

—
—

~5 min per iteration

The problem wasn't the tests — there were barely any. The problem was that the business logic had grown entangled with the networking layer. It expected network objects as input. Two things that had no reason to know about each other had become inseparable.

The fix was architectural: redraw the boundary. Pull the networking module out. Give the business logic only what it actually needs to do its job. Once the boundary was clean, the networking includes were gone, compile times dropped, and tests could run without any infrastructure at all.

The team went from two-hour iteration cycles to five minutes. Not because we wrote better code — because we put the right code in the right place.

Why this works

Fifteen years of large C++ systems across multiple industries.

I've worked in finance, games, startups, and enterprise infrastructure. The domains differ. The structural failure patterns don't. Business logic that has grown entangled with infrastructure. Modules that accreted responsibilities they were never meant to own. Boundaries that were never drawn, or drawn wrong and never corrected.

Recognising those patterns quickly is the job. I prioritise reading systems end-to-end rather than relying on IDE-assisted navigation — it's the only way to understand how a codebase actually behaves, versus how it was intended to behave. That approach, applied across enough large codebases, produces reliable structural intuition.
